# Вход через Telegram — разбор плана глазами атакующего (05.11)

Чат «Безопасность сайта JARVIS». Разбирался `team/site/review/ACCOUNT_PLAN.md` (коммит 4631b4c). Код входа не писался.

## Вывод
Схема «виджет Telegram → проверка подписи на Worker → подписанная cookie, базы нет» правильная: на сервере нечего
красть. Но в плане не хватает пяти вещей, и без них условие владельца («данные не вытащить») не выполняется:

1. **Токен бота на Worker'е.** Взлом Worker'а или Cloudflare-аккаунта даст атакующему токен @jarvibet-бота:
   он сможет писать в канал и читать переписку бота. **Решение: на Worker хранить не токен, а `SHA256(токен)`.**
   Для проверки подписи нужен только он, а с ним нельзя вызвать Bot API. Ещё надёжнее отдельный бот только для входа
   (без прав в канале), если владелец согласен.
2. **Как данные входа попадают на сайт.** В режиме `data-auth-url` (перенаправление) id, имя, `hash` и фото уходят
   в адресной строке, а значит в историю браузера, логи Cloudflare и Referer. **Решение:** режим с функцией
   обратного вызова (`data-onauth`) и `POST` на `/api/login`, либо перенаправление OAuth, где ответ приходит
   в `#tgAuthResult` (часть адреса после `#` на сервер не уходит). Этот путь Telegram не документирует, его надо проверить на домене. Сразу после входа стирать её через `history.replaceState`.
3. **`sha256(соль + telegram_id)` не обезличивает.** id Telegram — около 10 цифр, всего ~10¹⁰ вариантов. Если таблица
   утечёт вместе с солью, видеокарта переберёт их за минуты. **Решение:** `HMAC-SHA256(секрет, id)`, причём секрет
   хранится в секретах Worker'а, а не рядом с таблицей. По 152-ФЗ это всё равно псевдоним, то есть персональные данные.
4. **Захват чужого кабинета при варианте «код через бота» (п. 3 плана).** Атакующий показывает жертве свой код
   («отправь боту, получишь бонус»), жертва отправляет его, и браузер атакующего входит как жертва. Это известная
   фишинговая атака на вход по коду устройства. Если этот вариант всё-таки выбирать: бот перед подтверждением пишет
   «Войти на сайт с нового устройства? Если код дали вам другие люди, нажмите Нет», код одноразовый, ≥ 8 символов,
   живёт 5 минут. **Рекомендация: виджет, не код.**
5. **Главный реальный риск — не сайт, а аккаунты.** Тот, кто войдёт в Cloudflare, GitHub (секрет SITE_TOKEN, репозиторий сайта),
   BotFather или к регистратору домена, подменит скрипт кабинета, и он отдаст всё. **Нужно:** двухфакторная защита
   (лучше ключ или приложение, не SMS) на всех четырёх; токен Cloudflare для выкладки Worker'а — только «Workers:
   edit» одного аккаунта; SITE_TOKEN — fine-grained, только репозиторий сайта, только contents.

## Что упущено (по пунктам)

| # | Дыра | Как атакуют | Что сделать |
|---|---|---|---|
| 1 | Cookie нельзя отозвать | Украденная cookie живёт 30 дней; «Выйти» стирает её только в своём браузере | Срок 7–14 дней; в cookie номер ключа (`kid`): «выйти везде» = сменить ключ |
| 2 | Cookie на чужом домене | Worker на `*.workers.dev` при сайте на другом домене — сторонняя cookie: браузеры её режут, а `SameSite=None` открывает CSRF | Worker на том же домене (маршрут `/api/*`); имя `__Host-jv`, без `Domain` |
| 3 | Проверка `Origin` | `SameSite=Strict` не спасает от запросов с поддомена и старых браузеров | На `POST /api/*` — сверять `Origin` с нашим доменом, иначе 403 |
| 4 | `auth_date` | В плане сначала «не старше суток», потом «10 минут»; дата из будущего не проверяется | Одно правило: 0 ≤ сейчас − `auth_date` ≤ 300 с (+60 с на расхождение часов) |
| 5 | Повтор подписанного ответа | Перехваченный ответ виджета годен весь срок | Срок 5 мин (п. 4); по желанию — `hash` одноразовый (KV на 10 мин) |
| 6 | Строка проверки подписи | Строят из своего списка полей: лишнее поле или пропуск ломает сверку либо пропускает подмену | Все пришедшие поля, кроме `hash`, по алфавиту, `\n`; сравнение `timingSafeEqual`; `id` — только цифры |
| 7 | Скрипт виджета — сторонний | `telegram.org/js/telegram-widget.js` на странице кабинета: план сам запрещает сторонние скрипты | Кнопка-ссылка на `oauth.telegram.org/auth?...` без их скрипта (п. 2 вывода) или виджет только на отдельной `/login`, без данных кабинета |
| 8 | Фото и имя | `photo_url` грузится с серверов Telegram, а имя `"><img onerror=…>` даёт XSS | Фото не показывать; имя — только `textContent`; на сервере имя не нужно вовсе |
| 9 | Где показать имя | Cookie HttpOnly, сервер имя забывает — значит, имя положат в `localStorage`, и любой XSS его прочтёт | Имя не показывать («Вы вошли через Telegram») или только первое имя, осознанно |
| 10 | Логи Cloudflare | Workers Logs / `wrangler tail` пишут адреса и `console.log`; при перенаправлении в адресе id и hash | Observability выключить или не логировать тело и адрес; `console.log` без данных |
| 11 | Заголовки на GitHub Pages | GitHub Pages не ставит заголовки; `frame-ancestors` в `<meta>` не работает → кликджекинг кнопки «Удалить» | Сайт за Cloudflare (Transform Rules / `_headers`), без этого вход не включать |
| 12 | Подмена скрипта в репозитории | Репозиторий сайта открытый, публикует Actions с SITE_TOKEN: утечка токена = свой JS в кабинете | CSP с хэшами скриптов, SRI; защита ветки в репо сайта; токен с минимальными правами (п. 5 вывода) |
| 13 | Отказ в обслуживании | Бесплатный Worker — 100 тыс. запросов в сутки; забили лимит — вход лежит (утечки нет, но кабинет недоступен) | Rate limiting binding или правило WAF на `/api/login`; кабинет работает и без входа (локально) |
| 14 | Домен | Перехват DNS или домена = свой сайт с «настоящим» виджетом | DNSSEC, блокировка переноса у регистратора, 2FA (п. 5 вывода) |
| 15 | Ошибки наружу | Стек и текст ошибки в ответе подсказывают устройство | Наружу только `{ok:false}` с кодом |

## Что лишнее
- **Rate limit от перебора подписи** — HMAC-SHA256 не перебрать; ограничение нужно только от нагрузки (п. 13).
- **CORS «только наш домен»** при Worker'е на том же домене не нужен вовсе: просто не отдавать `Access-Control-Allow-*`.
  Задавать `Allow-Credentials` с подстановкой Origin из запроса — частая дыра, лучше не включать.
- **Слияние избранного с сервером** — пока нет общего списка, нет и слияния; без хранилища этап 4 «Порядка работ» не нужен.

## Альтернатива, где персональных данных нет совсем
У проекта уже есть мини-приложение Telegram (`team/site/app/`). Внутри Telegram приходит подписанный `initData` с той же
проверкой. «Мои клубы» можно держать там (Telegram CloudStorage хранит их на стороне Telegram, а не у нас), а на сайте
оставить только избранное в браузере. Тогда у нас нет ни сервера с id, ни 152-ФЗ-вопроса о хранении. Решать владельцу.

## 152-ФЗ (не юридическая консультация — показать юристу)
- Проверка подписи на Cloudflare — уже **обработка** персональных данных (id, имя) за рубежом. Это требует уведомления
  РКН о трансграничной передаче (ст. 12) и упирается в требование первичного сбора в базах в РФ (ст. 18 ч. 5).
  «Cookie без базы» этот вопрос не снимает.
- Уведомление РКН об обработке, политика, согласие, срок, удаление — в плане есть, верно.
- Google Fonts и jsdelivr (`SECURITY_0411.md`, п. 4) — та же трансграничная передача IP уже сейчас.
